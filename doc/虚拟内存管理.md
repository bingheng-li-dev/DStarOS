# 虚拟内存管理

## 前置知识

### ELF文件的VMA和LMA

ELF中的每个section都会有这两个地址：VMA是运行时地址，LMA是加载/存放地址。如果通过readelf命令查看elf文件，例子：

```structured text
Sections:
Idx Name          Size      VMA       LMA       File off  Algn
  0 .text         00001000  08000000  08000000  00001000  2**2
  1 .data         00000200  20000000  08001000  00002000  2**2
```

- VMA：运行时地址，CPU取指/访存时用的地址。

- LMA：加载时地址，文件内容存放在 Flash/ROM 的地址。链接脚本中使用`AT(LMA)`指定物理内存地址。其决定了内核被放在了真实物理内存的地址，只是运行的时候CPU去认为放在了VMA，去VMA取指，取变量值。

- 普通 Linux 程序（用户态）：VMA = LMA，因为文件映射到进程虚拟地址空间。DStarOS链接脚本[lds\linker_qemu.ld，lds\linker_k210.ld]中的BASE_ADDRESS指定了VMA：

- ```structured text
  KERNEL_VA_OFFSET = 0xffffffc000000000;
  PHYS_BASE        = 0x80200000;
  BASE_ADDRESS     = PHYS_BASE + KERNEL_VA_OFFSET;
  SECTIONS
  {
      . = BASE_ADDRESS;
      ......
      .text : AT(ADDR(.text) - KERNEL_VA_OFFSET) {...}
  }
  ```

> 其中 `KERNEL_VA_OFFSET = 0xffffffc000000000` 是内核虚拟地址相对物理地址的固定偏移量，`BASE_ADDRESS`（即 VMA）就是物理基址 `PHYS_BASE` 加上这个偏移。开启 MMU 后内核唯一的映射关系即 `KVA = PA + KERNEL_VA_OFFSET`，完整方案见后文《DStarOS 内核虚拟地址偏移映射方案》。

-----------------------------------------------------------------

对于DStarOS内核，真正决定物理位置的有三层：

1. 链接器（决定 ELF 里写什么）

`AT()` 指令告诉链接器把每个段的 LMA 字段写成什么。

2. 加载器（决定按哪个字段放）

- **QEMU `-kernel kernel.elf`**：解析 ELF program headers，把每个 LOAD 段拷贝到 **`p_paddr`（LMA）** 指定的物理地址
- **QEMU `-kernel kernel.bin`**：忽略 ELF 信息，按 `-kernel` 命令行约定的地址放（通常是 `0x80200000`）
- **RustSBI**：作为 firmware 先于 kernel 启动，最后**硬编码跳转**到 PA `0x80200000`，所以无论 ELF 说什么，RustSBI 都会跳到 `0x80200000`

3. RustSBI 的硬编码入口

即使 ELF 的 `e_entry`（入口点）写的是 `0xFFFFFFC080200000`（高 VA），RustSBI 也不会读它——它只会跳转到约定好的 PA。所以 `_start` 的代码字节必须在 PA `0x80200000`。

### PC寄存器工作原理

首先指令（二进制机器码）长什么样？参考RISC v手册的指令集部分，每个32位指令哪几位代表什么意思都有。以jalr指令为例，RISC v手册介绍如下：

```
jalr rd, offset(rs1) 	t =pc+4; pc=(x[rs1]+sext(offset))&~1; x[rd]=t  
跳转并寄存器链接 (Jump and Link Register). I-type, RV32I and RV64I
把pc设置为 x[rs1] + sign-extend(offset)，把计算出的地址的最低有效位设为 0，并将原pc+4的值写入f[rd]。rd默认为x1。

+31-----------20+19----15+14----12+11-----7+6-----0+
|  offset[11:0] |   rs1  |   010  |   rd   |1100111|
+---------------+--------+--------+--------+-------+
```

PC （程序计数器）**存的是 “指令地址”，不是指令本身**；RV64 下 PC 是 64 位宽，但指令依然是 32 位（标准 RISC‑V），尽管指令都是32位，但是指令地址长度以及PC寄存器长度RV32是32位，RV64是64位。举个例子（RV64）：

```
0x0000000080000000:  jal ra, 0x10   ; 这条指令地址是 0x80000000
```

此时 **PC = 0x0000000080000000**（64 位地址），而不是指令的 32 位机器码。

------

CPU取指流程：

1. **取指 IF**：CPU 拿 PC 里的地址，**去内存读出** 32 位机器指令；
2. **译码 ID**：拆解 32 位二进制，识别是啥指令、用哪些寄存器、偏移多少；
3. **执行 EX**：算地址、算算术逻辑、跳转判断；
4. **回写 WB**：把结果写回通用寄存器，同时**更新下一条 PC**（受跳转指令影响则跳转或＋4（+4是因为一条指令是32位4字节的，前一条指令地址的往后一条自然是加4字节））。

总结一下：（offset具体看下一节相对寻址介绍）

```
PC 默认 +4 顺序执行

符号引用（函数/全局变量/标签）：
  距离 ≤ ±2GB → 链接器填 offset = VMA(目标) - VMA(自身)
                 auipc+addi（取地址）
                 auipc+jalr / jal（跳转调用）
                 beq/j 等（分支跳转，offset 直接编进指令）

  距离 > ±2GB → 链接器报错
                人工用数据槽存绝对 VA
                la + ld 取出绝对地址（auipc 在 ±2GB 内取数据槽地址）
                jr 跳转
```

取指和跳转是两回事，PC的修改要么默认执行时+4，要么跳转语句直接修改PC的值。

去取变量值的时候，auipc+addi改的也不是PC的值，只是通过PC的值去加上偏移量计算出变量的地址，这个后面会再强调。

------

<u>**重要的是，即使没有使能MMU，通过相对偏移寻址（相对偏移寻址原理在下一小节介绍），程序仍然可以正常运行。**</u>

**同时有了VMA和LMA后，PC取指的细节：**

PC的初始值：在上一小节已经说了，RustSBI 完成初始化后，直接用 `jr` / `jalr` 跳到固定物理地址 `0x80200000`，这是 QEMU virt 平台的硬约定。RustSBI **不读 ELF 的 `e_entry`字段**，它只知道"内核加载在 0x80200000，我就跳过去"。所以 `_start` 第一条指令执行时，PC = `0x80200000`， 64-bit ，真实物理地址。（别忘了在SBI中以M态运行时，PC也是使用的物理地址。）

**PC在什么时候存虚拟地址了呢？**

**"取指去哪"由 satp 决定，不由 VMA 决定**:PC 里存的数字是"虚拟地址"还是"物理地址"，完全取决于 `satp.MODE`：

```
satp.MODE = 0 (BARE)
  CPU 取指：直接把 PC 的值送到总线 → 物理地址
  PC = 0x80200000 → 取物理地址 0x80200000 处的指令 ✓

satp.MODE = 8 (Sv39)
  CPU 取指：把 PC 的值当 VA，查页表翻译 → 物理地址
  PC = 0x80200000 → 查页表 → 找不到映射 → Page Fault ✗
  PC = 0xFFFFFFC080200000 → 查页表 → 翻译出 0x80200000 → ✓
```

### 编译参数`-mcmodel=medany`与auipc+addi相对寻址

**`-mcmodel=medany`**为RISC v 64 gcc独有编译选项，也是DStarOS内核选择的编译选项。

**`-mcmodel`**指定内存寻址方式与代码模型：

- **`-mcmodel=medlow`**（小模型）：代码 + 数据必须在约**±2GiB 地址空间**内。`-mcmodel=medlow`：±2GB，窗口必须在绝对地址 0~2GB 之内，偏移从地址 0 算起，高内核地址直接不能用。
- **`-mcmodel=medany `**（中等任意模型）：可寻址范围同样在约**±2GiB 地址空间**内。`-mcmodel=medany` = "medium any"，含义是：
  - **medium**：用 auipc+addi 两条指令，32-bit 偏移，覆盖 ±2GB 窗口；
  - **any**：这个 ±2GB 窗口可以位于地址空间的**任意位置**（不要求在低 4GB 内），覆盖范围：[PC - 2GB, PC + 2GB]，这个窗口跟着 PC 走，PC 在哪里，窗口就在哪里；
- **`-mcmodel=large`**（大模型）：无 2GiB 限制。全功能 64 位寻址，代码体积大，极少使用。

因为 RISC-V 64 没有直接 64 位绝对寻址指令，**`medany`**强制指定符号地址通过 auipc 方式加载，即使用 PC 相对寻址（Program Counter Relative）访问符号；`auipc`将指定偏移量加到当前PC上，通过这种方式得到指令和符号地址，而不是加载写死的如0x80000000此类硬编码地址。

（偏移计算方法和原理在下面讲解）如果计算出存在超过2GB的相对偏移，会**直接在链接时报错**；偏移**在编译链接时就已经算好、写死进二进制里了**。CPU运行时不再计算，只是执行"PC + offset"。

**如果存在一次性跳转超过2GB的情形**，需要通过先把目标地址装进寄存器再跳转（通过la+ld+jr组合的方式，不考虑`-mcmodel=large`），不再靠auipc+addi相对寻址。

```asm
# 方案1：数据槽（trampoline 里用的就是这个）
.data
addr_slot: .dword target_addr   # 存绝对地址

.text
la   t0, addr_slot   # auipc+addi 取数据槽的地址（距离近，±2GB内）
ld   t0, 0(t0)       # 从数据槽加载 64-bit 绝对地址
jr   t0              # 跳到任意地址

# 方案2：编译器用多条指令拼出 64-bit 立即数（-mcmodel=large，极少用）
```

例子可以参考后面DStarOS内核偏移映射的 trampoline 将PC直接跳高地址，由于一次性跨越了超过2GB的地址空间，就使用了前述方法。

------

以如下这段C代码为例子讲解相对寻址，edata为链接文件指定的.data section的end address：

```C
unsigned int *dst = (unsigned int *)edata;
```

编译器生成:

```assembly
auipc a0, %upper_offset(edata) # PC + 高20位偏移
addi  a0, a0, %lower_offset(edata) # 加低12位偏移 → 得到符号地址
```

根据RISC v64指令集，其中：

| auipc rd, immediate         | x[rd] = pc + sext(immediate[31:12] << 12) | PC 加立即数  |
| --------------------------- | ----------------------------------------- | ------------ |
| **addi rd, rs1, immediate** | **x[rd] = x[rs1] + sext(immediate)**      | **加立即数** |

在auipc指令中，**`x[rd] = pc + sext(immediate[31:12] << 12)`**：

1. immediate立即数位于32为指令的第31-12位共20位（有符号数，补码存储），该指令首先将immediate左移12位（低12位填充0），得到32位值，例：`imm20=0x123` → `imm32=0x123000`；

2. sext为符号扩展到64位，将immediate的**最高位（bit31）**扩展到64位，也就是说若`immediate[31]=0`，高32位全0，反之全为1;
3. PC为AUIPC指令自身的64位地址**（非下一条指令）**；
4. 与当前指令地址PC相加：`rd = PC + sext(immediate)`。

例子：

设：

- AUIPC 指令地址 `PC = 0x0000000080000000`
- 汇编：`auipc t0, 0x1`（`imm20=0x1`）

计算：

1. `imm20=0x1`
2. `imm32=0x1 << 12 = 0x1000`
3. `sext(0x1000) = 0x0000000000001000`（bit31=0，高 32 位为 0）
4. `t0 = 0x80000000 + 0x1000 = 0x80001000`

immediate20 是 20 位有符号数（范围：-2^19 ~ 2^19-1） ，左移 12 位后，偏移量范围：±2^31 字节（±2GB） 可覆盖当前 PC 前后各 2GB 地址空间。因为低12位补0，可以看到有低12位的地址盲区，**因此auipc总是与addi指令配对使用**。

在addi指令中，**`x[rd] = x[rs1] + sext(immediate)`**：immediate是12位有符号数（补码），通过sext符号位扩展到64位（因为是RISC v64，寄存器是64位）。

因此，auipc的取值范围-2¹⁹ （−524288）~ +2¹⁹ - 1（524287）左移12位（× 4096）变成-2³¹~+2³¹ - 4096（负向极限Δmin=−524288×4096=-2³¹=−2147483648；正向极限Δmax=524287×4096=2³¹−4096=2147479552）；addi的取值范围[-2¹¹, 2¹¹-1] = [-2048, 2047]，加起来为[-2³¹-2¹¹，2³¹-2¹¹-1]=[-2147485184≈-2GB（比-2GB还要小一点点），+2147481599≈+2GB]字节。（实际上因为addi只能取到正向2047字节，所以正向差了2048字节范围，负向同理会多一些范围）（2GB=2³¹=2147483648）。

------

现在来看如何通过这种方法进行相对寻址。

auipc+addi只是将偏移值offset拆成了两部分，本质只是对PC作偏移操作。

然后C代码中做的事情，是要将edata的值做为地址赋值给指针dst。首先在RV64中，edata是64位的地址，在链接脚本中为64位高位虚拟地址（比如为0xFFFFFFC080201000)。**要把edata赋值给dst，自然需要先寻edata的址，取到它的值（edata地址存储的值）**。

首先该64位地址被强制转换为了32位的(unsigned int *)类型，强制类型转换只是告诉编译器：“把这个地址当成指向 32 位整数的指针”，注意并没有真正将64位的edata截断，它仍然是64位的。这个强制类型转换事实上不会影响编译出的汇编指令（auipc+addi），只是拿给编译器看的。这里要复习一下C语言的基础指针知识，dst是(unsigned int *)类型的指针，在RV64下，dst本身仍然是64位的，它存储了一个64位的地址，这个地址指向一个32位的(unsigned int)类型的数据。edata同理。

倒推offset = 64位符号地址(edata) - 64位指令地址(PC)，按照前面介绍的过程，对offset（不是对edata）取高20位和低12位，变成指令中的立即数。在最后offset加在PC上，实现偏移寻址。

**需要注意的是：**

执行auipc语句时，pc里存放的是auipc的地址（PC0），执行完，a0中存放PC0 + offset0高20位偏移；此时PC1=PC+4，执行addi，addi加的也是同样的offset0的低12位偏移，即相对于PC0的偏移；执行完，a0中存放的是PC0 + 完整的offset0，这个PC0指的是auipc指令的地址，offset0也是edata相对于auipc指令的偏移量。PC2=PC1+4。除了自然+=4，只有跳转语句修改PC的值。寻址不需要PC跳转。

------

**重点是这个偏移值offset是怎么来的？**

是链接时，由链接器填写的。

已知链接器的目标是：让 `la t0, some_func` 执行完之后，`t0` 里存的是 `some_func` 的地址。参考RISC-V手册，la伪指令会被展开为auipc+addi或auipc+ld。

`auipc+addi` 执行的运算是：

```
t0 = PC + offset
```

链接器知道两件事：

- `auipc` 执行时 PC = `VMA(auipc指令)`（这是链接器对运行时的预期）
- 希望 `t0` = `VMA(some_func)`

所以倒推 offset：

```
t0               = PC      + offset
VMA(some_func)   = VMA(auipc指令) + offset

offset = VMA(some_func) - VMA(auipc指令)
```

CPU 运行时只是机械地执行 `PC + 已编码的数字`，完全不知道 VMA 是什么。

------

从头捋一下：

- **编译阶段（单个 .c → .o）**

编译器**不知道最终 VMA**，只生成**重定位条目**（relocation entry）：

```
# 编译器生成的汇编（伪代码）：
auipc  t0, %pcrel_hi(some_func)    ← 占位符，值未定
addi   t0, t0, %pcrel_lo(some_func)

# .o 文件里附带重定位表：
R_RISCV_PCREL_HI20  offset=xxx  symbol=some_func
R_RISCV_PCREL_LO12  offset=xxx  symbol=some_func
```

offset 此时是 0 或占位值，**还没算**。

- **链接阶段（多个 .o → elf）**

链接器把所有 .o 合并，分配好每个符号的最终 VMA，然后：

```
1. 查重定位表，找到每条 auipc 指令
2. 计算 offset = VMA(some_func) - VMA(该auipc指令)
3. 检查 offset 是否在 ±2GB 内，超出则报错
4. 把 offset 高20位填进 auipc 的 imm20
         低12位填进 addi 的 imm12
```

所以符号地址分配和 offset 计算**都在链接阶段**完成，编译阶段只是留下"这里需要填一个 pcrel offset"的标记。

- **跨文件 vs 同文件**

没有本质区别，链接器统一处理：

```
同一 .o 内的符号引用  → 编译器可能预填，但链接器仍会 relocate
跨 .o 的符号引用      → 必须链接器填
```

都是同一套重定位机制，链接器是唯一知道所有符号最终 VMA 的角色。

### 为什么 MMU 关闭时，通过相对寻址，VMA也可以正常运行

相对寻址加载方式，即使在链接脚本中修改为```BASE_ADDRESS = 0x80200000;```=>```BASE_ADDRESS = 0xFFFFFFC080200000;```，即在链接脚本中就加上虚拟高地址，**即使尚未启动MMU，代码仍能正常运行**。

为什么？

链接器预期：`PC = VMA(auipc指令)`，但 MMU 关闭时 `PC = LMA(auipc指令)`。

看起来 PC 不对，但：

```
offset = VMA(some_func)   - VMA(auipc指令)
       = (LMA(some_func)   + KERNEL_VA_OFFSET)
       - (LMA(auipc指令)   + KERNEL_VA_OFFSET)
       = LMA(some_func)   - LMA(auipc指令)
                              ↑ KERNEL_VA_OFFSET 抵消了
```

offset 的值和 KERNEL_VA_OFFSET（含义见前文 ELF 小节）无关，只取决于两者的**相对距离**，而这个距离在 VMA 空间和 LMA 空间里完全相同。

所以：

```
运行时（MMU关）：
t0 = LMA(auipc指令) + offset
   = LMA(auipc指令) + LMA(some_func) - LMA(auipc指令)
   = LMA(some_func)   ← 正确的物理地址 ✓
```

------

但是直接/间接写死加载地址的代码如**数据段里存储的绝对地址**（函数指针表、回调表）：

```C
/* 编译后 .rodata 里写入的是 0xFFFFFFC08021xxxx（高 VA） */
void (*handlers[])(void) = { handler0, handler1 };
```

在未开启MMU时，直接访问该地址0xFFF……会导致程序跑飞。

开启MMU后，**指针**存储的值需要通过pa_to_kva将存储的绝对物理地址更新为虚拟地址。

## RISC v虚拟内存

### RISC v 基于页面的虚拟内存

按照RISC v手册的说法：

> RISC-V 的分页方案以 SvX 的模式命名,其中 X 是以位为单位的虚拟地址的长度。RV32 的分页方案 Sv32 支持 4GiB 的虚址空间，这些空间被划分为 2^10个 4 MiB 大小的巨页。 每个巨页被进一步划分为 2^10个 4 KiB 大小的基页（分页的基本单位）。因此， Sv32 的页表是基数为 2^10的两级树结构。页表中每个项的大小是四个字节，因此页表本身的大小是 4 KiB。页表的大小和每个页的大小完全相同，这样的设计简化了操作系统的内存分配。
>
> 
>
> RV64 支持多种分页方案，但我们只介绍最受欢迎的一种， Sv39。 Sv39 使用和 Sv32 相同的 4 KiB 大的基页。页表项的大小变成 8 个字节，所以它们可以容纳更大的物理地址。为了保证页表大小和页面大小一致，树的基数相应地降到 2^9，树也变为三层。 Sv39 的 512 GiB 地址空间划分为 2^9个 1 GiB 大小的吉页。每个吉页被进一步划分为 2^9 个巨页。在Sv39 中这些巨页大小为 2 MiB，比 Sv32 中略小。每个巨页再进一步分为 2^9个 4 KiB 大小的基页。 

另外还有Sv48，Sv57等，这里不考虑。DStarOS基于RV64，使用Sv39页表项，后续所有实现都基于Sv39页表项。

Sv39使用**39位**虚拟地址对应**56位**物理地址。（具体有多大物理地址空间与芯片厂商有关，这里就按理论56位算）

Sv39的39位虚拟地址长下面这样：

|  9位   |  9位   |  9位   | 12位  |
| :----: | :----: | :----: | :---: |
| VPN[2] | VPN[1] | VPN[0] | PGOFF |

Sv39的56位物理地址布局如下：

|  26位  |  9位   |  9位   | 12位  |
| :----: | :----: | :----: | :---: |
| PPN[2] | PPN[1] | PPN[0] | PGOFF |

 **页内偏移是12位，刚好2^12=4096，也就是一个物理/虚拟页的大小。**一个页为4K大小由来已久，因此架构师如是设计。

Sv39的页表项PTE布局如下：PTE中存储的永远是物理页号而不是虚拟内存页号

|  26位  |  9位   |  9位   |   2位    |          8位           |
| :----: | :----: | :----: | :------: | :--------------------: |
| PPN[2] | PPN[1] | PPN[0] | Reserved | D\|A\|G\|U\|X\|W\|R\|V |

根据RISC v手册，每个域的含义如下：

> - V 位决定了该页表项的其余部分是否有效（V = 1 时有效）。若 V = 0，则任何遍历到此页表项的虚址转换操作都会导致页错误。
> - R、 W 和 X 位分别表示此页是否可以读取、写入和执行。如果这三个位都是 0，那么这个页表项是指向下一级页表的指针，否则它是页表树的一个叶节点。
> - U 位表示该页是否是用户页面。若 U = 0，则 U 模式不能访问此页面，但 S 模式可以。若 U = 1，则 U 模式下能访问这个页面，而 S 模式不能。
> - G 位表示这个映射是否对所有虚址空间有效，硬件可以用这个信息来提高地址转换的性能。这一位通常只用于属于操作系统的页面。
> - A 位表示自从上次 A 位被清除以来，该页面是否被访问过。
> - D 位表示自从上次清除 D 位以来页面是否被弄脏（例如被写入）。  
> - RSW 域留给操作系统使用，它会被硬件忽略。  
> - PPN 域包含物理页号，这是物理地址的一部分。若这个页表项是一个叶节点，那么 PPN 是转换后物理地址的一部分。否则 PPN 给出下一节页表的地址。

### SATP寄存器/MMU

一个叫 satp（Supervisor Address Translation and Protection，监管者地址转换和保护）的 S 模式控制状态寄存器控制了分页系统。  SATP寄存器布局如下（这里只介绍RV64的64位寄存器布局）：

| 4位  | 16位 | 44位 |
| :--: | :--: | :--: |
| MODE | ASID | PPN  |

其中MODE 域可以开启分页并选择页表级数 ：

- 值为0代表BARE模式，不开启地址转换和保护，即不开启MMU；
- 值为8代表使用Sv39；
- 值为9代表使用Sv48。

ASID（Address Space Identifier，地址空间标识符）域是可选的，它可以用来降低上下文切换的开销。看操作系统用不用。

PPN 字段保存了**根页表的物理地址**，它以 4 KiB 的页面大小为单位。通常 M 模式的程序在第一次进入S模式之前会把零写入 satp 以禁用分页，然后 S 模式的程序在初始化页表以后会再次进行satp 寄存器的写操作。  

为什么PPN字段明明要写入根页表的物理地址，一个物理地址有56位，但是PPN域却只有44位！？因为这涉及到地址对齐的概念，根页表必须是页对齐（也就是4K对齐）的，物理地址 56 位，但页大小是 4K = 2^12，所以任何页表的起始地址低 12 位**永远是 0**。所以 `satp` 只需存高 44 位（PPN），使用时自动补 12 个 0 得到完整的 56 位物理地址。（地址对齐是架构规定的，像这样的对齐要求还有很多，参考.S汇编文件中的.align指令用法）

-----------------

当在 satp 寄存器中启用了分页时（即打开MMU）， S 模式和 U 模式中的虚拟地址会以从根部遍历页表的方式转换为物理地址。 注意这一过程是硬件实现的。在 RISC-V 中写 `satp` 开启 MMU 时，**下一条指令的 PC 就立刻被当作虚拟地址翻译**。**每当出现PC取指、`ld` / `sd` 数据访问，`jalr` / `call` 跳转目标**三种涉及地址的情况时，这些地址作为虚拟地址送入MMU硬件自动翻译为物理地址。

值得注意的是，尽管翻译过程是硬件自动完成的（硬件查找页表进行翻译，这也是为什么需要将根页表的物理地址写入SATP寄存器，翻译过程在下一节），但是**页表的维护、管理更新是由操作系统进行的。**这也是为什么DStarOS中，get_pte函数为什么存在。

MMU并不总是查找PTE:

> 如果所有取指， load和 store 操作都导致多次页表访问，那么分页会大大地降低性能！所有现代的处理器都用地址转换缓存（通常称为 TLB，全称为 Translation Lookaside Buffer）来减少这种开销。为了降低这个缓存本身的开销，大多数处理器不会让它时刻与页表保持一致。这意味着如果操作系统修改了页表，那么这个缓存会变得陈旧而不可用。 S 模式添加了另一条指令来解决这个问题。这条 sfence.vma 会通知处理器，软件可能已经修改了页表，于是处理器可以相应地刷新转换缓存。它需要两个可选的参数，这样可以缩小缓存刷新的范围。一个位于rs1， 它指示了页表哪个虚址对应的转换被修改了；另一个位于 rs2，它给出了被修改页表的进程的地址空间标识符（ASID）。如果两者都是 x0，便会刷新整个转换缓存。  

### MMU 硬件翻译虚拟地址的过程（Sv39）

> 补充：标准 RV64 只定义了 Sv39 / Sv48 / Sv57 三种分页方案，DStarOS 使用 Sv39（`satp.MODE = 8`），本节即以 Sv39 为准。

`satp` 写入根页表物理地址并把 `MODE` 置为 8 之后，硬件里的**页表遍历器（PTW，Page Table Walker）**会对每一个待翻译的虚拟地址自动完成「VA → PA」的转换，操作系统不参与这一步（OS 只负责把页表本身建好、并在改动后用 `sfence.vma` 刷新 TLB）。Sv39 是**三级**页表，记 `LEVELS = 3`、`PTESIZE = 8`（每个 PTE 8 字节）、`PAGESIZE = 4096`。

待翻译的 39 位 VA 被拆成三段 9 位的页表索引加 12 位页内偏移：

| VPN[2] (9位) | VPN[1] (9位) | VPN[0] (9位) | PGOFF (12位) |
| :----------: | :----------: | :----------: | :----------: |
| 第 2 级（根）索引 | 第 1 级索引 | 第 0 级索引 | 页内偏移 |

遍历算法（建议**对照 RISC-V 手册 10.6**章节，里面有易懂详细的转换过程）：

```
1. a = satp.PPN × PAGESIZE          // 根页表物理基址
   i = LEVELS - 1 = 2               // 从最高级开始

2. pte = mem[a + VA.VPN[i] × PTESIZE]
   // 注意：PTW 用“物理地址”直接读页表，本身不再经过翻译

3. if (pte.V == 0) || (pte.R == 0 && pte.W == 1)
       → page fault                 // 无效项，或 W 没有 R 的非法组合

4. if (pte.R == 1 || pte.X == 1)
       → 这是叶子 PTE，跳到第 5 步
   else                             // 指向下一级页表的指针
       a = pte.PPN × PAGESIZE
       i = i - 1
       if (i < 0) → page fault      // 三级走完仍未命中叶子
       回到第 2 步

5. // 找到叶子 PTE，按访问类型(取指/读/写)与特权级(S/U)检查 X/R/W、U 位
   //（含 SUM / MXR 等），不通过则相应的 page fault

6. if (i > 0 且 pte.PPN[i-1:0] != 0)
       → page fault                 // 大页未对齐（misaligned superpage）

7. // 拼出物理地址
   PA.PGOFF = VA.PGOFF
   if (i > 0)                       // 大页：低位 PPN 取自 VA
       PA.PPN[i-1:0]      = VA.VPN[i-1:0]
       PA.PPN[LEVELS-1:i] = pte.PPN[LEVELS-1:i]
   else                             // 4KiB 基页：三段 PPN 全取自叶子 PTE
       PA.PPN = pte.PPN

8. // 置 pte.A = 1；若为写访问再置 pte.D = 1（A/D 更新）
```

第 4 步是关键分叉：`R/W/X` 三位**全为 0** 表示这个 PTE 只是“指向下一级页表的指针”，需继续往下走；只要 `R` 或 `X` 有一位为 1，它就是**叶子**，遍历结束。这正是前文 PTE 域说明里“若 R、W、X 都是 0，则该项指向下一级页表”的硬件含义。

**大页（superpage）**：如果在第 2 级（i=2）就遇到叶子，映射的是一个 **1 GiB 吉页**；在第 1 级（i=1）遇到叶子，映射 **2 MiB 巨页**；走到第 0 级才是普通 **4 KiB 基页**。大页能减少页表层数与 TLB 项，但要求物理基址按页大小对齐（即第 6 步的检查）。

一个 4 KiB 基页的完整例子，设 `VA = 0x0000000080201000`（低地址、bit38=0 的合法 Sv39 地址）：

```
VA      = 0x80201000
PGOFF   = VA[11:0]   = 0x000
VPN[0]  = VA[20:12]  = 0x001   (1)
VPN[1]  = VA[29:21]  = 0x001   (1)
VPN[2]  = VA[38:30]  = 0x002   (2)
```

遍历：

```
i=2: 读 mem[root_pa + 2×8]   → PTE2(指针)  → pmd_pa = PTE2.PPN×4096
i=1: 读 mem[pmd_pa  + 1×8]   → PTE1(指针)  → pt_pa  = PTE1.PPN×4096
i=0: 读 mem[pt_pa   + 1×8]   → PTE0(叶子, R/W/X≠0)
PA = PTE0.PPN×4096 + 0x000   = 物理地址
```

这三级（根页表 → 中间页表 → 末级页表）正对应 `get_pte` 里依次访问的 **PGD → PMD → PTE 页**。区别在于：**硬件 PTW 用物理地址访问这三页**，而 `get_pte` 是**软件**遍历同样的三页——MMU 开启后软件的每次访存都要走翻译，所以 `get_pte` 必须把每一级页表页的物理地址 `pa_to_kva()` 成内核虚拟地址后再解引用（详见后文《为什么页表页本身也受影响》）。

最后，VA 的高 25 位（bit 63:39）在 Sv39 下必须等于 bit 38（符号扩展），否则地址“不规范（non-canonical）”会直接触发异常。内核地址 `0xFFFFFFC0_xxxxxxxx` 高位全 1、`VPN[2] = 0x1FF`，正是落在高半区的合法内核地址；`KERNEL_VA_OFFSET = 0xffffffc000000000` 取这个值，就是为了让它恰好对齐到 Sv39 的符号扩展边界上。

## DStarOS 内核虚拟地址偏移映射方案

前面已经介绍了相对寻址的概念，也介绍了为什么通过相对寻址，即使还没有打开 MMU，直接加载虚拟地址也可以寻址。简单地说，PC 被 SBI 硬跳转到 0x80200000 的物理地址，offset 又是相对 PC 的偏移量，跟虚拟地址还是物理地址无关，因为偏移量是一样的，又是相对寻址，所以可以正常跑。

### 偏移映射的核心原则

DStarOS 采用**偏移映射（线性映射）**：内核空间里每个物理地址都映射到固定偏移之外的一个虚拟地址，并且全内核只有这一条映射：

```
KVA = PA + KERNEL_VA_OFFSET   (KERNEL_VA_OFFSET = 0xffffffc000000000)
```

`pa_to_kva()` / `kva_to_pa()` 就是这条公式的正反向换算。

接下来要反复用到、也是后文所有“陷阱”的根源的一条硬件事实：

> **MMU 开启后，CPU 执行的每一条取指、load/store 指令所发出的地址，都被硬件当作虚拟地址（VA）送入页表翻译，不再直接作为物理地址访问内存。**

因此 MMU 开启后，凡是要拿一个地址去读写内存（解引用指针），这个地址就必须是已经建立映射的 VA（内核里即 KVA）；若仍拿物理地址当指针，CPU 会把它当 VA 翻译——要么找不到映射触发 page fault，要么命中错误的页造成静默损坏。

恒等映射（VA = PA）只在 trampoline 切换页表的那几页临时存在，`vmm_remove_identity_mapping()` 调用后即撤销，之后 PA 不再能直接访问。

下面几节都是这条原则在不同场景下的具体表现。

注意内核偏移映射维护所有直到MEMORY_END的映射表而非仅仅是KERNEL_END。

### get_pte：软件遍历 Sv39 三级页表

无论是建立映射（`init_kernel_offset_mapping`）还是查询映射（`vmm_remove_identity_mapping`、缺页处理），底层都落到同一个原语：[src/kernel/vmm.c](../src/kernel/vmm.c) 的 `get_pte()`。它是前文《MMU 硬件翻译虚拟地址的过程》里那套硬件 PTW 的**软件版**——同样沿 PGD→PMD→PTE 三级走，区别在于由 CPU 跑 C 代码来读写页表，因此每一级页表页的访问都要受 MMU 当前状态影响。

```c
static pte_t *get_pte(ppn_t pgd_ppn, virAddr_t va, bool create, bool mmu_enabled);
```

四个参数：

| 参数 | 含义 |
| --- | --- |
| `pgd_ppn` | 根页表（PGD）所在物理页号，即 satp 的 PPN 域 |
| `va` | 要查询/建立映射的虚拟地址 |
| `create` | `true`：中间级缺失就 `alloc_page()` 补建，**总是**返回末级 PTE 槽；`false`：任一级缺失立即返回 `NULL`（只读查询） |
| `mmu_enabled` | `true`：访问页表页要先 `pa_to_kva()`；`false`（MMU 未开）：物理地址可直接当指针 |

#### 取三段索引

VA 的三段 9 位 VPN 由宏取出（见 `memtype.h`）：

```c
#define PGD(va) (((va) >> 30) & 0x1FF)   // VPN[2]，第 2 级（根）索引
#define PMD(va) (((va) >> 21) & 0x1FF)   // VPN[1]，第 1 级索引
#define PTE(va) (((va) >> 12) & 0x1FF)   // VPN[0]，第 0 级索引
```

#### 逐级下降（以第一级 PGD 为例）

```c
phyAddr_t pgd_pa = convert_ppn2pa(pgd_ppn);
pte_t *pgd = mmu_enabled ? (pte_t *)pa_to_kva(pgd_pa) : (pte_t *)pgd_pa;  // 选 KVA 还是 PA
if (!pte_is_valid(pgd[pgd_idx]))           // 本级条目无效（PTE_V == 0）
{
    if (!create) return NULL;              // 只读查询：缺级即失败
    pframe_t *new_pmd_frame = alloc_page(); // 否则新建下一级页表
    if (!new_pmd_frame) return NULL;
    new_pmd_frame->reference += 1;
    pgd[pgd_idx] = pte_create(convert_pframe2ppn(new_pmd_frame), 0); // 写“指针型”PTE
}
// 取出下一级页表 PPN，进入 PMD 级重复同样动作……
phyAddr_t pmd_pa = convert_ppn2pa(pgd[pgd_idx] >> PTE_PPN_OFFSET);
```

第二级 PMD 完全同理，第三级拿到末级 PTE 页后：

```c
pte_t *pte = mmu_enabled ? (pte_t *)pa_to_kva(pte_pa) : (pte_t *)pte_pa;
if (!create && !pte_is_valid(pte[pte_idx])) return NULL;
return &pte[pte_idx];   // create=true 时即使该 PTE 还没填，也返回它的“槽地址”由调用者写入
```

#### 三个关键点

- **指针型 PTE vs 叶子 PTE**：中间级用 `pte_create(ppn, 0)` 写入，标志位里 `R/W/X` 全为 0，表示“这是指向下一级页表的指针”（对应硬件 PTW 第 4 步的分叉）；叶子 PTE 则由调用者用 `pte_create(ppn, PTE_R|…)` 至少置一位。注意 `pte_create` 内部**总会**或上 `PTE_V`：
  ```c
  static inline pte_t pte_create(ppn_t ppn, pteflg_t flag) {
      return (pte_t)((ppn << PTE_PPN_OFFSET) | flag | PTE_V);  // PTE_PPN_OFFSET = 10
  }
  ```
  所以中间级 PTE 是“有效（V=1）但 R/W/X=0”的合法指针项。`pgd[idx] >> PTE_PPN_OFFSET` 就是反向把 PPN 从 PTE 里取出来。

- **`create` 的两副面孔**：`init_kernel_offset_mapping` 建表时传 `true`，让 get_pte 顺带把缺失的 PGD/PMD/PTE 页一路补齐，返回空槽供其 `*pte = pte_create(...)` 填写；查询/拆映射（如 `vmm_remove_identity_mapping`）传 `false`，只走不建，缺级即返回 `NULL`。

- **`mmu_enabled` 为何存在**：这正是全文那条原则的落点——同样一段三级遍历，MMU 关时三页页表用 PA 直接解引用，MMU 开后必须 `pa_to_kva()` 成 KVA 再解引用，否则 CPU 会把 PA 当 VA 翻译而 page fault。所以 get_pte 把状态作参数交给调用者显式指定：建表阶段传 `false`，运行期（缺页等）传 `true`。

### init_kernel_offset_mapping建立偏移映射

跳高之前，必须先把内核页表本身建好——这条 `KVA = PA + KERNEL_VA_OFFSET` 的映射不是 CPU 自带的，而是软件一项一项填进页表的。负责这件事的是 [src/kernel/vmm.c](../src/kernel/vmm.c) 里的 `init_kernel_offset_mapping()`。

**调用时机**：`os_init_before_mmu_enable` → `vmm_init()` → `init_kernel_offset_mapping()`，发生在 **MMU 尚未启用**时。这一点决定了它访问页表帧时一律把物理地址直接当指针用（`get_pte` 的 `mmu_enabled` 参数传 `false`）——此时 PA 即可直接访问。

#### 第一步：分配根页表（PGD）

```c
pframe_t *kernel_pgd_pframe = alloc_page();          // 向 PMM 要一页做根页表
memset((void *)convert_pframe2pa(kernel_pgd_pframe), 0, PGSIZE);  // 清零（全部 PTE_V=0）
kernel_pgd_pframe->reference += 1;
vmm_kernel_pgd_ppn = convert_pframe2ppn(kernel_pgd_pframe);       // 记下根页表 PPN
```

`vmm_kernel_pgd_ppn` 就是后面 startup.S 里 `la t1, vmm_kernel_pgd_ppn; ld t1, 0(t1)` 取出、拼进 satp 的那个根页表物理页号。Sv39 一页页表恰好 512 个 8 字节 PTE，其中索引 `[0,255]` 对应低半区（用户空间），`[256,511]` 对应高半区（内核偏移映射就落在这里）。

#### 第二步：按链接脚本分段、赋不同权限建立偏移映射

内核内存布局（由 ld 决定）是 `skernel → .text → .rodata → .data → .bss → ekernel → 其余物理内存`。函数据此取出三个分界 PPN，把 `[skernel, MEMORY_END)` 切成三段，分别赋不同权限：

| 物理范围 | 段 | PTE 权限 |
| --- | --- | --- |
| `[skernel, etext)` | `.text` 代码 | `PTE_G \| PTE_R \| PTE_X` |
| `[etext, erodata)` | `.rodata` 只读数据 | `PTE_G \| PTE_R` |
| `[erodata, MEMORY_END)` | `.data`/`.bss` + 内核之外的全部物理内存 | `PTE_G \| PTE_R \| PTE_W` |

每一段的循环体都是同一个套路（以 `.text` 段为例）：

```c
for (ppn_t ppn = ppn_skernel; ppn < ppn_etext; ppn++)
{
    // 注意传入的 VA 是 pa_to_kva(pa) = 高 VA；建立的就是 高VA → 该物理页 的映射
    pte_t *pte = get_pte(vmm_kernel_pgd_ppn, pa_to_kva(convert_ppn2pa(ppn)), true, false);
    *pte = pte_create(ppn, PTE_G | PTE_R | PTE_X);   // 槽里写入 物理 ppn + 权限位
}
```

要点：
- 传给 `get_pte` 的虚拟地址是 `pa_to_kva(pa)`（高 VA），写进 PTE 的却是**物理** `ppn`——这一取一存，建立的正是「高 VA → PA」一条偏移映射。
- `pte_create(ppn, flags)` 把物理页号左移到 PTE 的 PPN 域再或上权限位；`PTE_X`/`PTE_W` 的有无让 `.text` 不可写、`.rodata` 不可写不可执行，实现 W^X 的段保护。

#### 为什么映射到 MEMORY_END 而不是 KERNEL_END，以及 PTE_G

映射范围一直铺到 `MEMORY_END`（而非内核镜像结尾），把**全部物理内存**都永久映射进高 VA 区。这样内核任何时候都能 `pa_to_kva(pa)` 拿到任意物理帧的可访问指针——例如某个物理帧被分配给用户进程后，它会有两份映射：用户页表里一份（进程自己用），内核页表里这一份（内核随时能通过 KVA 读写它，如 copy-on-write 复制页内容时）。

所有条目都带 `PTE_G`（Global）：该映射对所有 ASID 有效，只有 `sfence.vma zero, zero`（全刷）才会清除，按 ASID 刷的 `sfence.vma rs1, asid` 不会动它。当前 DStarOS 还没有 ASID 切换，全刷场景下 G 位无害也无益；将来若启用 ASID，内核高位映射常驻 TLB 就能减少 miss。

#### get_pte 如何按需补齐三级页表

`get_pte(..., create=true, ...)` 沿 Sv39 三级走，缺哪级就补哪级：用 `PGD(va)/PMD(va)/PTE(va)` 取出三段 9 位索引，若某级中间页表项无效（`PTE_V=0`）就 `alloc_page()` 新建一页中间页表、把它的 ppn 以「R/W/X 全 0」的指针型 PTE 写回上一级，最后返回末级 PTE 槽地址。由于此刻 `mmu_enabled=false`，它对 pgd/pmd/pte 三页都直接用物理地址解引用（`(pte_t *)pgd_pa`，不套 `pa_to_kva`），这与「MMU 开启后必须 `pa_to_kva`」恰好相反——根因还是那条原则：地址被当 PA 还是 VA，取决于 MMU 此刻开没开。

#### 第三步：为 trampoline 段额外建恒等映射

最后给 `[_trampoline_start, _trampoline_end)` 这几页再建一条 **VA = PA** 的恒等映射，让 MMU 一开、PC 还在低地址时仍能取指（详见下一节「trampoline 跳高」）：

```c
extern char _trampoline_start[], _trampoline_end[];
phyAddr_t tramp_pa_start = (phyAddr_t)_trampoline_start;   // 见下方“坑”
phyAddr_t tramp_pa_end   = (phyAddr_t)_trampoline_end;
for (ppn_t ppn = convert_pa2ppn_flr(tramp_pa_start); ppn < convert_pa2ppn_cil(tramp_pa_end); ppn++)
{
    // VA 直接传 PA（convert_ppn2pa），建立的就是 VA = PA 的恒等映射
    pte_t *pte = get_pte(vmm_kernel_pgd_ppn, convert_ppn2pa(ppn), true, false);
    *pte = pte_create(ppn, PTE_G | PTE_R | PTE_X);
}
```

这里有个容易踩的**坑**：本函数在 MMU 关闭时运行，`la _trampoline_start` 用的是相对寻址，offset 抵消了 `KERNEL_VA_OFFSET`，所以 `(phyAddr_t)_trampoline_start` 取到的**本来就是物理地址**，绝不能再套 `kva_to_pa()`（那会再减一次偏移得到错误值）。作为对照，`vmm_remove_identity_mapping()` 是在 MMU 已开、PC 已是高 VA 时调用的，那里 `_trampoline_start` 拿到的才是 VA，必须 `kva_to_pa()` 还原成 PA 去定位同一条恒等映射 PTE 并清零。

#### 收尾

函数返回时，内核页表里已经同时有了「整段物理内存的高 VA 偏移映射」和「trampoline 的临时恒等映射」两套条目，根页表 PPN 也写进了 `vmm_kernel_pgd_ppn`。接下来 startup.S 取这个 PPN 拼出 satp、写入、再靠下面讲的 trampoline 把 PC 抬到高 VA。

### trampoline 跳高：把 PC 从物理地址切换到高虚拟地址

偏移映射在概念上很简单，但在**启动那一刻**有一个绕不开的难题：内核被链接在高虚拟地址（`BASE_ADDRESS = PHYS_BASE + KERNEL_VA_OFFSET`），可是 RustSBI 把 PC 硬跳到的是物理地址 `0x80200000`。开启 MMU 的前后，PC 的值必须从低物理地址“跳”到对应的高虚拟地址——这就是 trampoline 要做的“跳高”。相关代码在 [src/kernel/startup.S](../src/kernel/startup.S)。

#### 为什么必须跳高

开 MMU 前，`_start` 在 PA `0x80200000` 上运行，靠相对寻址（offset 抵消了 `KERNEL_VA_OFFSET`，见前文）一切正常，此时 PC ≈ `0x802xxxxx`。

一旦 `csrw satp` 写入并开启 Sv39，**下一条指令的 PC 就立刻被当作 VA 送去翻译**。而内核页表里的偏移映射只建立了 `高 VA → PA` 这一条；并没有 `VA 0x80200000 → PA 0x80200000`。如果此时放任 PC 仍停在低地址 `0x802xxxxx`，下一次取指就会查页表 → 找不到映射 → page fault。

所以 MMU 一开，就必须把 PC 从低物理地址 `0x80200000` 改成它对应的高虚拟地址 `0xFFFFFFC080200000`，让取指落到偏移映射覆盖的范围里。

这一跳的距离正好是 `KERNEL_VA_OFFSET ≈ 0xffffffc000000000`，**远超 ±2GB**，所以 `auipc+addi`（相对寻址，±2GB 窗口）无法表达，必须用前文《编译参数 -mcmodel=medany》里讲的**数据槽方案**：把目标的 64 位绝对 VA 存进一个 `.dword`，再 `la + ld + jr` 装进寄存器后跳过去。

#### 鸡生蛋问题：为什么需要 trampoline 段 + 恒等映射

跳高本身也要执行几条指令（`csrw satp`、`sfence.vma`、`la/ld/jr`）。问题在于：**`csrw satp` 这条指令一执行完，MMU 就已经开了**，紧接着的 `sfence.vma`、`la`、`ld`、`jr` 仍然位于低物理地址 `0x802xxxxx`，它们的取指也要过页表翻译。如果这段过渡代码所在的页没有映射，MMU 刚一打开、还没来得及跳高就 page fault 了。

解决办法：把这段过渡代码单独放进 `.text.trampoline` 段，并在内核页表里为它额外建立一条**恒等映射（VA = PA）**。于是 MMU 开启后的瞬间，PC（仍是低地址）落在恒等映射里，取指依然有效，过渡代码得以执行到 `jr` 那一步把 PC 抬到高 VA。等成功跳高、进入高地址内核后，这条恒等映射就没用了，由 `vmm_remove_identity_mapping()` 撤销——之后低物理地址不再能直接当指针访问（这也是后文各种“物理地址泄露”bug 的前提）。

所以内核启动期间页表里同时存在两套映射：

```
偏移映射  高 VA 0xFFFFFFC0_80200000... → PA 0x80200000...   （覆盖整个内核，永久）
恒等映射  低 VA 0x80200000...          → PA 0x80200000...   （只覆盖 trampoline 几页，临时）
```

#### startup.S 实现逐步拆解

**第一步，开 MMU 前（低物理地址，`.text.entry`）：**

```asm
    call  os_init_before_mmu_enable     # 建好内核页表：偏移映射 + trampoline 恒等映射，
                                        # 并把根页表 PPN 写入 vmm_kernel_pgd_ppn
    li    t0, SATPMODE_RV39             # 0x8000000000000000，satp.MODE = 8 (Sv39)
    la    t1, vmm_kernel_pgd_ppn
    ld    t1, 0(t1)                     # 取出根页表 PPN
    or    a0, t0, t1                    # a0 = MODE | pgd_ppn，即待写入 satp 的值
    la    t0, _trampoline_start         # 相对寻址（仍在低地址，±2GB 内可达）
    jr    t0                            # 进入 trampoline
```

注意此前 `la sp, boot_stack_top1` 设的也是**低物理地址**的栈（相对寻址，offset 抵消），并用 `mv s0, a0` 把 core id 暂存到被调用者保存寄存器 `s0`，使其跨越两个 `os_init_*` 调用都不丢。

**第二步，trampoline 跳高（`.text.trampoline`，恒等映射 PA = VA）：**

```asm
_trampoline_start:
    csrw  satp, a0                  # 使能 MMU。此刻起取指走页表；
                                    # 后续指令靠恒等映射继续有效
    sfence.vma zero, zero           # 刷新 TLB

    la    t0, _start_virtual_addr   # 恒等映射内，相对寻址可达这个数据槽
    ld    t0, 0(t0)                 # 读出槽里存的 .dword = _start_virtual 的高 VA 绝对值
    jr    t0                        # PC ← 高 VA，正式跳高 ✓

    .align 3
_start_virtual_addr:
    .dword _start_virtual           # 数据槽：链接器把 _start_virtual 的 64 位高 VA 写在这里
```

这里就是数据槽方案的落地：`_start_virtual` 被链接在高 VA，链接器把它的 64 位绝对地址填进 `_start_virtual_addr` 这个 `.dword`。`la t0, _start_virtual_addr` 取的是**数据槽自身**的地址（离 PC 很近，±2GB 内，`auipc+addi` 没问题），`ld` 再把里面的高 VA 取出来，`jr` 跳过去。如果直接写 `la t0, _start_virtual; jr t0`，`la` 会展开成 `auipc+addi`，而 `_start_virtual` 距当前 PC 超过 2GB → **链接期直接报错**。

**第三步，跳高之后（`.text`，高虚拟地址）：**

```asm
_start_virtual:
    bnez  s0, 1f
    la    sp, boot_stack_top1       # core0：重新设栈，这次 la 算出的是“高 VA”的栈
    j     2f
1:  la    sp, boot_stack_top2       # core1 的栈
2:  mv    a0, s0                    # core id 作参数
    call  os_init_after_mmu_enable
```

进入高地址后第一件事是**重设 sp**：之前的 sp 是低物理地址的栈，现在 PC 已是高 VA，`la sp, boot_stack_top1` 自然算出同一个栈的高 VA 版本，与当前地址空间一致。随后带着 core id 调用 `os_init_after_mmu_enable`，内核正式在高虚拟地址上运行（该函数内部会做 `PageListBegin`、`FreeList` 等指针的 PA→KVA 修正，并撤销 trampoline 恒等映射）。

> 小结：trampoline 跳高 = 「**先给过渡代码留一条恒等映射，开 MMU 后靠它撑住取指，再用数据槽 + jr 把 PC 一次性抬到高 VA，最后撤掉恒等映射**」。它解决的是“开 MMU 那一瞬间 PC 还在低地址、而内核只认高地址”这个先有鸡还是先有蛋的过渡难题。

### 为什么打开 MMU 后，get_pte 中的页表项需要转换为虚拟地址

承接上面的核心原则，看一个最典型的场景——`get_pte` 遍历页表：

**MMU 关闭时：**

```
CPU 发出地址 0x80201000
    ↓ （无翻译）
DRAM 0x80201000  ← 直接访问
```

此时 `(pte_t *)pgd_pa` 里存的 `0x80201000` 就是 DRAM 实际位置，解引用没问题。

**MMU 开启后（偏移映射）：**

页表建立的映射是：

```
VA 0xFFFFFFC080201000  →  PA 0x80201000
```

没有建立 `VA 0x80201000 → PA 0x80201000` 这条映射（恒等映射只有 trampoline 那几页临时存在，随后被 `remove_identity_mapping` 清掉）。

此时代码里仍用原来的 PA 作指针：

```c
pte_t *pgd = (pte_t *)pgd_pa;   // pgd_pa = 0x80201000
*pgd;                            // CPU 把 0x80201000 当 VA 走页表
```

CPU 查页表，发现 `0x80201000` 没有有效映射 → **Page Fault**，或者更糟——恒等映射还存在时会碰巧命中别的物理页，造成**静默的数据损坏**（访问到了错误的物理内存）。

**正确做法：用 KVA 访问：**

```c
pte_t *pgd = (pte_t *)pa_to_kva(pgd_pa);
// pa_to_kva(0x80201000) = 0x80201000 + 0xffffffc000000000
//                       = 0xFFFFFFC080201000
*pgd;   // CPU 查页表，找到映射 → PA 0x80201000 → 正确访问
```

### 为什么页表页本身也受影响

`get_pte` 遍历三级页表（PGD → PMD → PTE 页），每一级都要读写那一页的内容。这些页表页也在物理内存里，地址同样是 PA。MMU 开启后访问它们，**CPU 同样会把地址当 VA 走翻译**——所以每一级都需要 `pa_to_kva`：

```c
// 第一级：根页表
pte_t *pgd = mmu_enabled ? (pte_t *)pa_to_kva(pgd_pa) : (pte_t *)pgd_pa;

// 第二级：从 PTE 取出 PMD 的 PPN，转 PA，再转 KVA
phyAddr_t pmd_pa = convert_ppn2pa(pgd[pgd_idx] >> PTE_PPN_OFFSET);
pte_t *pmd = mmu_enabled ? (pte_t *)pa_to_kva(pmd_pa) : (pte_t *)pmd_pa;

// 第三级：同理
phyAddr_t pte_pa = convert_ppn2pa(pmd[pmd_idx] >> PTE_PPN_OFFSET);
pte_t *pte = mmu_enabled ? (pte_t *)pa_to_kva(pte_pa) : (pte_t *)pte_pa;
```

PTE 里存的 PPN 本身不需要转换（它只是一个数字，写进寄存器或页表项），但要**访问 PPN 指向的那页内存**时就必须转成 KVA。

## MMU 开启后的常见陷阱：物理地址泄露

### 问题的本质

承接前文《偏移映射的核心原则》——MMU 开启后内核只有 `KVA = PA + KERNEL_VA_OFFSET` 一条映射，把物理地址当指针解引用必然出错：

```
写 PA（如 0x80440000）→ MMU 查页表，找不到 → Store page fault
读 PA（如 0x80437000）→ MMU 查页表，找不到 → Load page fault
```

这类 bug 的统一特征：**某个函数内部把物理地址当成 C 指针直接解引用**，在 MMU 关闭时工作正常（此时 PA 即可直接访问），在 MMU 开启后必然 page fault。

---

### 物理地址泄露的三种典型形式

#### 形式一：内存分配函数内部清零

PMM 的 `alloc()` 找到空闲帧后，需要把物理页清零。原始实现：

```c
phyAddr_t *dst = (phyAddr_t *)convert_pframe2pa(ret);  // PA
while (...) { *dst++ = 0; }  // MMU 开启后 → Store page fault at PA
```

`convert_pframe2pa()` 语义上返回的就是物理地址，把它直接强转成指针写入，在 MMU 关闭时正常，在 MMU 开启后必然崩溃。

**修法**：根据 MMU 状态选择地址：

```c
phyAddr_t frame_pa = convert_pframe2pa(ret);
void *zero_dst = mmu_is_enabled() ? (void *)pa_to_kva(frame_pa) : (void *)frame_pa;
memset(zero_dst, 0, (size_t)nsize * PGSIZE);
```

`mmu_is_enabled()` 读 `satp.MODE`（高 4 位非零表示 MMU 已启用）：

```c
static inline bool mmu_is_enabled(void) {
    return (read_csr(satp) >> 60) != 0;
}
```

#### 形式二：分配器返回值是物理地址

`kmalloc` 大块分配路径的原始实现：

```c
pframe_t *tmp = alloc(...);           // tmp 是 KVA 的 pframe_t *（PMM fixup 之后）
ret = (void *)convert_pframe2pa(tmp); // 换算出 PA，返回给调用者
```

调用者（VFS、proc、vmm）拿到这个值，直接做 `ptr->field = ...`，就是在写物理地址 → page fault。

这类 bug 的诊断特征是：sbadaddr 打印出来是一个偏小的物理地址（如 `0x80437188`），不是 KVA，而且偏移量精确对应某个结构体字段。

**修法**：返回之前加 `pa_to_kva`：

```c
phyAddr_t frame_pa = convert_pframe2pa(tmp);
ret = mmu_is_enabled() ? (void *)pa_to_kva(frame_pa) : (void *)frame_pa;
```

#### 形式三：释放时用 PA 做范围判断，KVA 永远无法命中

`kfree` 需要判断指针属于 micro pool 还是大块分配。原始实现以 PA 做比较：

```c
phyAddr_t pool_pa = convert_pframe2pa(MicroPhysicalMemoryPoolBase); // ≈ 0x80201000
if (pool_pa < (phyAddr_t)ptr && ...)  // ptr 是 KVA ≈ 0xffffffc080201080
```

KVA 始终远大于 PA，`pool_pa < KVA` 恒为真，但 `KVA < pool_pa + 2*PGSIZE` 恒为假（差了整个 KERNEL_VA_OFFSET）。micro pool 的指针永远通不过检查，全部落入大块路径，`convert_pa2pframe_flr` 拿 KVA 当 PA 算出错误的 pframe → **PMM 链表静默损坏**。

这类 bug 不会立刻 page fault，而是在后续某次分配/释放时触发更难定位的错误，因此比前两种更危险。

**修法**：统一归一化到 PA 再做比较：

```c
phyAddr_t ptr_pa = mmu_is_enabled() ? kva_to_pa((virAddr_t)ptr) : (phyAddr_t)ptr;
phyAddr_t pool_pa = convert_pframe2pa(MicroPhysicalMemoryPoolBase);
if (pool_pa < ptr_pa && ptr_pa < pool_pa + 2 * PGSIZE)
    microDemalloc(ptr);  // microDemalloc 内部用原始指针操作 pool，传 ptr 而非 ptr_pa
```

---

### 诊断方法速查

| 现象 | 可能的原因 |
|---|---|
| Store page fault，sbadaddr 是一个 `0x802xxxxx` 的物理地址 | 某处把 `convert_pframe2pa()` 的返回值直接当指针写 |
| Load page fault，sbadaddr 是结构体字段的物理地址 | 分配函数返回了 PA，调用者访问结构体字段时触发 |
| 运行一段时间后 PMM/kmalloc 崩溃，堆栈不合理 | kfree 做了错误的范围判断，损坏了 PMM 链表 |
| 只在 MMU 开启后出现，MMU 关闭时一切正常 | 以上三种情况的通用特征 |

---

### 规则总结

1. **`convert_pframe2pa()` 的返回值是数字，不是指针**。要通过它读写物理页内容，必须先 `pa_to_kva()`。
2. **`kmalloc`/`alloc` 的返回值，MMU 开启后必须是 KVA**。调用者不应该再手动加 `pa_to_kva`。
3. **`kfree` 接收的指针类型必须与 `kmalloc` 返回的类型一致**。如果 `kmalloc` 返回 KVA，`kfree` 里做地址算术前必须先 `kva_to_pa`。
4. **任何需要在 MMU 开启前后两个阶段都能调用的函数**，用 `mmu_is_enabled()` 判断当前状态，分别选 PA 或 KVA。

## DStarOS用户态（U态）程序虚拟地址方案

虚拟地址解决的核心问题是：

- **隔离性**：每个进程有独立的地址空间，互不干扰；
- **安全性**：进程无法直接访问物理内存，必须经过 MMU 检查；
- **灵活性**：内存可以不连续、可以换页到磁盘、可以共享；
- **简化编程模型**：每个程序都认为自己独占内存，从 0 开始。

和内核使用偏移映射方案不同，用户态不是一条固定的线性映射，而是**每个进程一套、按需建立、可以不连续**的映射：

- 内核：全物理内存 `KVA = PA + KERNEL_VA_OFFSET` 一条线性映射，所有 hart/进程共享，落在 PGD 高半区 `[256,511]`，PTE 不带 `PTE_U`。
- 用户：每个进程用一组 **VMA** 描述自己用到的若干虚拟区间，物理页可零散分配（甚至先不分配、缺页时再给），映射落在 PGD 低半区 `[0,255]`，PTE 带 `PTE_U`（U 态可访问）。

相关代码在 [src/kernel/vmm.c](../src/kernel/vmm.c) 与 [src/kernel/include/vmm.h](../src/kernel/include/vmm.h)。

> **当前阶段说明**：`vmm_mm_create()` 创建 `mm_t` 时把 `pgd_ppn` **默认**设为 `vmm_kernel_pgd_ppn`，但 `fork` 路径（`copy_proc_mm`）会为用户进程**另行分配一张独立 PGD** 并覆盖这个默认值——所以经由 fork 产生的用户进程已经拥有**独立的根页表**（分配新根页表 + 复制内核高半段 `[256,511]`，详见下文《线程模块与虚拟内存的衔接》）。仍待完善的是写时复制（COW）等优化，见 TODO。

### 关键数据结构

**`mm_t`（`struct mm_struct`）—— 进程地址空间描述符**，一个进程一个：

| 字段 | 含义 |
| --- | --- |
| `pgd_ppn` | 进程根页表（PGD）物理页号；写进 satp 即切换到该地址空间 |
| `mmap_list` | VMA 链表头，链表按 `vm_start` 升序串起本进程所有区间 |
| `map_count` | VMA 数量 |
| `brk_start` / `brk_current` | 堆（brk）的起始与当前边界，用于 `sbrk` 式增长 |

**`vma_t`（`struct vm_area_struct`）—— 一段连续虚拟区间**，一个进程可有多个（代码段、数据段、堆、栈……各一段）：

| 字段 | 含义 |
| --- | --- |
| `vm_start` / `vm_end` | 区间 `[vm_start, vm_end)`，左闭右开 |
| `vm_flag` | 保护标志：`VMP_R`/`VMP_W`/`VMP_X` 的组合，可附加 `VMA_HEAP` 标记堆区 |
| `proc_mm` | 反向指回所属 `mm_t` |
| `vma_list_linker` | 把本 VMA 挂入 `mm->mmap_list` 的链表结点 |

一个进程的地址空间 = `mm_t` 一个 + 若干 `vma_t` 串在 `mmap_list` 上。VMA 只描述“这段地址是合法的、什么权限”，**不等于已经分配了物理页**——是否落实到物理页取决于即时分配还是懒分配。

### 核心接口

| 函数 | 作用 |
| --- | --- |
| `vmm_mm_create()` | 新建并初始化 `mm_t`（空 `mmap_list`） |
| `vmm_mm_destroy(mm)` | 解映射全部 VMA、归还物理帧、释放所有 `vma_t` 与 `mm_t` |
| `vmm_mm_copy(dst, src)` | fork：把 src 的全部 VMA 与已映射物理页深拷贝到 dst |
| `vmm_vma_create(start, end, flag)` | 新建一个 `vma_t`（此时 `proc_mm=NULL`，尚未挂入） |
| `vmm_vma_insert(mm, vma)` | 按 `vm_start` 升序把 VMA 挂入 `mm`，`map_count++` |
| `vmm_vma_get(mm, va)` | 在 `mmap_list` 中查找包含 `va` 的 VMA |
| `vmm_map_vma(mm, vma)` | **即时分配**：为整段区间逐页 `alloc_page` 并建 PTE |
| `vmm_unmap_vma(mm, vma)` | 解映射整段区间，按引用计数归还物理帧 |
| `vmm_page_fault_handler(badva, type)` | **懒分配**：缺页时按所属 VMA 分配单页 |

### 典型用法与流程

#### 1. 建立一段用户区间

```c
mm_t *mm = vmm_mm_create();
// 建立一段可读写的用户数据区 [0x10000, 0x12000)
vma_t *vma = vmm_vma_create(0x10000, 0x12000, VMP_R | VMP_W);
vmm_vma_insert(mm, vma);     // 挂入进程地址空间（此刻还没有物理页）
```

挂好 VMA 后有两种落实物理页的方式：

- **即时分配（eager）**：`vmm_map_vma(mm, vma)` 立刻为 `[vm_start, vm_end)` 每页 `alloc_page`、清零、建 PTE。适合必须立即保证内存存在的场景。
- **懒分配（lazy，默认）**：什么都不做，等进程真正访问到某页、触发 page fault 时再分配。省内存、启动快。

#### 2. 懒分配：缺页处理

进程访问尚未映射的页 → MMU 触发 page fault → trap 进入 `vmm_page_fault_handler(badva, fault_type)`：

```c
mm_t *mm = TaskCurrent->proc_mm;            // 取当前进程地址空间（内核线程 mm=NULL → panic）
vma_t *vma = vmm_vma_get(mm, badva);        // badva 落在哪个 VMA？
if (!vma) panic("segfault");                // 不在任何 VMA → 非法访问

// 权限检查：写错误要求 VMP_W，取指错误要求 VMP_X
if (fault_type == 2 && !(vma->vm_flag & VMP_W)) panic("segfault");
if (fault_type == 0 && !(vma->vm_flag & VMP_X)) panic("segfault");

pframe_t *frame = alloc_page();             // 分配并清零一页
memset((void *)convert_pframe2kva(frame), 0, PGSIZE);
virAddr_t page_va = badva & ~(PGSIZE - 1);  // 对齐到页边界
pteflg_t  flags   = vma_prot_to_pte_flags(vma->vm_flag);
pte_t    *ptep    = get_pte(mm->pgd_ppn, page_va, true, true);  // create=true, mmu_enabled=true
*ptep = pte_create(convert_pframe2ppn(frame), flags);
tlb_flush_va(page_va);                      // 刷新该 VA 的 TLB，返回后重执行出错指令
```

要点：VMA 决定“地址合法 + 权限”，缺页处理负责“补上物理页”；越界（找不到 VMA）或越权（写只读、执行不可执行段）一律按段错误 panic。

#### 3. VMA 查找与堆边界

`vmm_vma_get` 顺着 `mmap_list` 找 `vm_start <= va < vm_end` 的区间。对带 `VMA_HEAP` 的堆区有特殊处理：即使 `va` 落在 VMA 范围内，只要 `va >= mm->brk_current`（超过当前堆顶）也算越界返回 NULL——这样堆 VMA 可以预留一个较大的 `vm_end`，而实际可用上界由 `brk_current` 动态控制。

#### 4. 权限转换

用户 VMA 的 `vm_flag` 通过 `vma_prot_to_pte_flags()` 转成 PTE 标志位，**总是带上 `PTE_U`**（U 态可访问），这是用户映射与内核映射的根本区别（内核映射绝不能带 `PTE_U`）：

```c
pteflg_t flags = PTE_U;                  // 用户页必带
if (prot & VMP_R) flags |= PTE_R;
if (prot & VMP_W) flags |= PTE_W;
if (prot & VMP_X) flags |= PTE_X;
```

#### 5. fork：vmm_mm_copy

`fork` 时 `vmm_mm_copy(dst, src)` 遍历 src 的每个 VMA：在 dst 里建一个范围/权限相同的新 VMA，再逐页把 src 已映射的物理页 `memcpy` 到子进程**新分配**的物理页（独立副本）。未映射的页（懒分配还没触发的）不复制，留给子进程将来缺页时再分配。`brk_start/brk_current` 一并复制。

> 当前是 **Eager Copy**（立即整页复制）；写时复制（COW，父子先共享只读、写时再分裂）留待后续，见 TODO。

#### 6. 销毁

`vmm_mm_destroy(mm)` 用 `list_for_each_safe` 遍历 `mmap_list`，对每个 VMA 先 `vmm_unmap_vma`（按引用计数归还物理帧、清 PTE、刷 TLB）、再从链表摘下、`vmm_vma_destroy` 释放描述符，最后 `kfree(mm)`。注意 `vmm_unmap_vma` 按 `frame->reference` 归零才 `dealloc`，为将来 COW 共享帧的引用计数语义预留。

### 小结

```
进程
 └── mm_t (pgd_ppn=进程根页表, mmap_list, brk)
        └── mmap_list: vma_t → vma_t → vma_t ...   (按 vm_start 升序)
                         每个 vma_t = [vm_start,vm_end) + 权限
                                        └── 物理页：即时(map_vma) 或 懒分配(page_fault)
                                                       PTE 带 PTE_U，落在 PGD[0..255]
```

VMA 是“地址空间的账本”（哪段合法、什么权限），物理页和 PTE 是“账本的兑现”（实际给没给内存）。二者分离，才能支持懒分配、COW、文件映射这些机制。

### 线程模块与虚拟内存的衔接

地址空间不是凭空切换的，它由进程/线程模块（[src/kernel/proc.c](../src/kernel/proc.c)）在 `pcb_t`、`fork`、`switch_to` 三处与 VMM 串起来。

#### pcb_t 里的两个相关字段：proc_mm 与 satp

每个进程的 `pcb_t` 持有：

- `mm_t *proc_mm`：本进程的地址空间描述符。**内核线程的 `proc_mm` 为 `NULL`**（它们只跑在内核高半区，不需要用户 VMA）。`vmm_page_fault_handler` 正是用 `TaskCurrent->proc_mm` 取当前地址空间，为 `NULL` 时直接判为内核缺页 panic。
- `ctx_t proc_context` 中的 `satp` 字段：保存该进程**应当加载的 satp 值**（`SATPMODE_RV39 | pgd_ppn`）。地址空间“是哪一张页表”最终就体现在这个 satp 上。

新进程在 `allocNewProc()` 里给出默认值：

```c
pcb->proc_context.satp = SATPMODE_RV39 | vmm_kernel_pgd_ppn;  // 默认用内核页表
pcb->proc_mm           = NULL;                                 // 默认是内核线程
```

用户进程的这两个字段随后在 `copy_proc_mm` 里被覆盖。

#### fork：copy_proc_mm 如何复制地址空间

`do_fork()` 创建子进程时调用 `copy_proc_mm(clone_flags, pcb)`，按是否带 `CLONE_VM` 分两条路：

**(1) 内核线程 fork（`CLONE_VM`）—— 共享地址空间：**

```c
if (clone_flags & CLONE_VM) {
    pcb->proc_mm = TaskCurrent->proc_mm;   // 直接共享父的 mm（内核线程通常都是 NULL）
    return ENO0_NO_ERROR;
}
```

子线程与父共享同一个 `mm`（satp 也仍是 `allocNewProc` 设的内核页表），不复制任何页。

**(2) 用户进程 fork —— 建立独立地址空间：**

```c
mm_t *mm = vmm_mm_create();                       // 新建 mm（pgd_ppn 默认=内核，下面覆盖）

pframe_t *new_pgd_frame = alloc_page();            // ① 分配一张独立根页表
memset((void *)convert_pframe2kva(new_pgd_frame), 0, PGSIZE);
new_pgd_frame->reference += 1;
mm->pgd_ppn = convert_pframe2ppn(new_pgd_frame);   // ② 设好独立 PGD（必须在 copy 之前）

// ③ 复制内核高半段 PGD[256..511]，让子进程也能访问内核地址空间
memcpy((void *)pa_to_kva(convert_ppn2pa(mm->pgd_ppn))          + sizeof(pte_t) * 256,
       (void *)pa_to_kva(convert_ppn2pa(vmm_kernel_pgd_ppn))   + sizeof(pte_t) * 256,
       sizeof(pte_t) * 256);

vmm_mm_copy(mm, TaskCurrent->proc_mm);             // ④ 深拷贝父的全部 VMA 与物理页到新页表

pcb->proc_mm           = mm;                        // ⑤ 挂上独立地址空间
pcb->proc_context.satp = SATPMODE_RV39 | mm->pgd_ppn;  // ⑥ satp 指向独立 PGD
```

几个关键点：

- **③ 为什么要复制内核高半段**：子进程有了自己的根页表后，低半区 `[0,255]` 装它自己的用户映射，但内核代码/数据始终在高半区 `[256,511]`。把内核 PGD 的高 256 项 `memcpy` 过来（拷的是指向同一批内核 PMD/PTE 页的指针项），子进程在 S 态处理 trap/系统调用时才仍能看到内核——这也是“所有进程共享同一套内核映射”的实现方式。
- **② 必须先设 `mm->pgd_ppn` 再 `vmm_mm_copy`**：`vmm_mm_copy` 内部用 `get_pte(dst->pgd_ppn, ...)` 往**目标页表**写 PTE，pgd_ppn 没设好就会写错页表。
- **④ 深拷贝**：`vmm_mm_copy` 逐 VMA、逐已映射页分配新帧并 `memcpy` 内容（Eager Copy），父子物理页彼此独立。未映射的懒分配页不复制，留给子进程将来缺页再补。
- **⑥** 子进程的 satp 从此指向自己的 PGD，下次被调度上 CPU 时由 `switch_to` 加载。

#### switch_to：通过 satp 完成地址空间切换

上下文切换 `switch_to(from_ctx, to_ctx)`（汇编，见 [src/kernel/cpua.S](../src/kernel/cpua.S)）除了存取被调用者保存寄存器，还负责**切换页表**——这正是地址空间隔离落地的一步。`ctx_t` 的内存布局里 `satp` 排在最后（偏移 14×8 字节），紧跟 `ra/sp/s0..s11` 之后：

```asm
switch_to:
    # ... 保存 from 的 ra/sp/s0~s11 到 from_ctx ...
    csrr t0, satp
    sd   t0, 14*REGBYTES(x10)     # 保存 from 的 satp（x10 = 第一个参数 from_ctx）

    # ... 恢复 to 的 ra/sp/s0~s11 ...
    ld   t0, 14*REGBYTES(x11)     # 取出 to 的 satp（x11 = 第二个参数 to_ctx）
    csrw satp, t0                 # 写入 → 切换到目标进程的页表
    sfence.vma zero, zero         # 全刷 TLB，丢弃旧地址空间的缓存翻译
    ret                           # ret 用的是刚恢复的 to 的 ra，回到目标进程
```

要点：

- `csrw satp` 一执行，**取指/访存立刻改用新页表翻译**。因为内核高半区在每个进程页表里都映射成同一套，所以紧接着的 `sfence.vma`、`ret` 等内核指令在新页表下依然有效——这与启动时 trampoline 跳高要解决的是同一类“切页表瞬间 PC 必须仍可翻译”的问题，只是这里靠“内核高半段处处一致”天然满足。
- `sfence.vma zero, zero` 是**全刷**（对应内核映射的 `PTE_G` 全局项也只有全刷才清）。当前未启用 ASID，每次切换都全刷；将来引入 ASID 后可改为按 ASID 刷，配合 `PTE_G` 减少 TLB miss。
- 内核线程之间切换时，各自 `satp` 其实都是内核页表，`csrw` 写的是同一个值，等于没换页表、只换了寄存器与栈。

把三处连起来看：`fork` 给用户进程备好独立 PGD 并把目标 satp 记进 `pcb->proc_context.satp` → 调度选中该进程 → `switch_to` 把这个 satp 写进 CSR，地址空间就切过去了。

### 跨 hart TLB Shootdown

`sfence.vma`（即 `tlb_flush_va` / `tlb_flush_all`）的作用域严格限制在**执行它的那个 hart**，不会自动广播到其他 hart。RISC-V spec 明确规定：该指令只使当前 hart 的地址翻译缓存对此前的页表写操作可见。

**需要跨 hart 刷 TLB 的场景**：

| 操作 | 是否需要跨 hart 刷 |
|---|---|
| 修改内核页表（所有 hart 共用同一页表） | 是 |
| 解除某进程映射，该进程可能正在另一 hart 上运行 | 是 |
| 给当前 hart 独占的进程新增映射 | 否（新增映射不会命中他人 TLB） |

**DStarOS 当前为何暂时安全**：

`vmm_remove_identity_mapping`（唯一修改共享内核页表的操作）在 `core2Enable()` 之前执行，hart 1 尚未启动；调度器无 SMP 进程迁移，进程页表由调度到它的 hart 独占，不存在一个 hart 修改另一个 hart 正在用的 PTE 的情况。

**将来引入 SMP 迁移或动态修改共享内核页表时**，需要改用 SBI 提供的跨 hart 接口：

```c
// sbi.h 中已有声明
sbi_remote_sfence_vma(hart_mask, start, size);
// 向 hart_mask 指定的 hart 集合发 IPI，令其执行 sfence.vma(start, size)
```

届时将 `tlb_flush_all()` / `tlb_flush_va()` 改为包装 `sbi_remote_sfence_vma` 对所有在线 hart 广播即可。在此之前，现有本地 `sfence.vma` 已满足需求。

### 引入 ASID 后可改为按 ASID 刷，配合 `PTE_G` 减少 TLB miss
